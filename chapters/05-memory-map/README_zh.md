# 05 —— 一个地址由谁回答？

本章把 ROM、SRAM 和寄存器端点连接到一条 Wishbone 主总线，声明字节地址图，检查对齐与重叠，然后运行固件访问各区域的首末字。

| 区域 | 字节地址范围 | 容量 | 用途 |
| --- | --- | ---: | --- |
| ROM | `0x00000000–0x00000fff` | 4 KiB | 复位代码和固件 |
| SRAM | `0x00010000–0x00010fff` | 4 KiB | 可写数据和栈 |
| Registers | `0x20000000–0x20000fff` | 4 KiB | 探测、读回和完成标志 |

## 地址译码解决什么问题？

译码器根据地址选择哪个设备可以应答。例如访问 `0x00010000` 应到 SRAM，访问 `0x20000000` 应到寄存器端点。同一地址最多应该属于一个设备；空洞里没有设备，不应误命中旁边的存储器。

`memory_map.py` 中的检查器是软件侧的一致性检查。真正把 ROM、SRAM 和寄存器接进主总线的是 LiteX SoC 区域。CSV 同时写出字节地址和字地址，便于检查地址单位转换。

## 常见问题

### 为什么 Wishbone 地址和固件地址不一样？

固件和地址图使用字节地址。本章 32 位 Wishbone 接口按字寻址，每加一代表 4 字节。比如 SRAM 末字的字节地址是 `0x00010ffc`，总线看到的地址为 `0x00010ffc / 4 = 0x000043ff`。数据和 byte select 仍决定这个字里的哪些字节有效。

### 地址译码和仲裁是一回事吗？

不是。译码根据地址选从设备；仲裁是在多个主设备同时请求共享总线时决定谁先使用。本章只有 CPU 一个主设备，因此检查地址译码和应答，不加入多主设备仲裁。

### 地址重叠或未映射会怎样？

地址重叠表示两个区域同时认领同一段地址，检查器会在 CPU 仿真前拒绝。本章单元检查故意添加重叠区域，并要求 `validate()` 抛出错误。对于 `0x30000000` 的未映射读，没有目标应答；CPU trap handler 把 `mcause=5`（load access fault）写到测试端点，运行器要求这个故障标志并确认没有正常完成标志。

### 怎样分辨到底哪部分出了问题？

不同层次分别留下证据：地图检查在构建前指出重叠；总线地址和选中的区域说明有效请求应该去哪；CPU trap handler 在没有设备回答时记录架构级 load fault。查看波形和运行日志，可以把地址图错误与固件读值不匹配区分开。

### 声明一张地址表就自动有译码器了吗？

没有。表格或 CSV 只是约定。本章由 LiteX bus region 把 ROM、`wishbone.SRAM` 和寄存器从设备连接到主总线；地图检查器提前验证计划中的字节范围。第 06 章会把这份手工约定与 LiteX Builder 生成的地址图比较。

## 运行与观察

```sh
PYTHONHASHSEED=0 python3 chapters/05-memory-map/run.py
```

正常固件检查 ROM 首末字、SRAM 首末字和寄存器读回，再写完成标志。负例固件从未映射地址 `0x30000000` 读取。查看 `results/05/memory_map.csv`、`results/05/run.log` 和 `results/05-unmapped/` 下的记录。

端点 ACK 在时钟沿寄存，使应答和所选中的事务对齐。ACK 表示请求已完成；没有 ACK 时，即使总线上碰巧出现数据，也不算完成读操作。

## PASS 能证明什么？

地图单元测试证明区域满足对齐、不重叠，且边界地址只命中预期区域。正常 CPU 仿真证明访问到达指定目标。未映射负例证明地址空洞会变成 load access fault，而不是返回陈旧数据或误报完成。第 06 章继续检查 LiteX 自动生成的系统地址图。
