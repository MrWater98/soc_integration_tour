# 20A：把内部状态移出来，再故意造几个坏点

本章有两个独立的RTL实验：**四位计数器的内部扫描**和**小RAM的March读写测试**。不需要开发板、GDB或OpenOCD。我们直接用测试平台驱动引脚，观察一个本来藏在电路内部的状态。

这章回答的问题是：芯片即使能启动，也可能有某个内部触发器或存储位坏了；如何主动把这种故障暴露出来？

## 一、先运行，再看文件

在教程根目录：

```sh
python chapters/20a-dft-basics/run.py
```

默认扫描链4位，RAM深度8、数据宽度8位，共8字节。RAM参数可以变化：

```sh
python chapters/20a-dft-basics/run.py --depth 16 --width 4 --output results/20a-parameters
```

扫描4位是本章固定的教学模型；它不是芯片扫描链的规定长度。RAM深度必须是支持的2次幂，以便本实验逐个注入地址位故障。

```text
scan_counter.sv + tb_scan.sv → Icarus编译 → scan.vvp
                                             │ 正常/扫描两种模式，逐个注入故障
                                             └→ cases/scan-*/scan.csv、run.log
ram_model.sv + tb_ram.sv     → Icarus编译 → ram.vvp
                                             │ March序列，逐个注入故障
                                             └→ cases/ram-*/march.csv、run.log
全部日志 → run.py比较预期 → summary.json + REPORT.md
```

完整实验RTL和测试平台也复制在`results/20a/rtl/`，sources.json记录哈希。CSV不是随机生成的数据，而是实际RTL仿真中逐个时钟/操作输出的记录。

## 二、为什么正常输出看不见全部状态？

打开[scan_counter.sv](scan_counter.sv)：

```verilog
reg [3:0] q;
assign normal_out = q[0];
```

内部有四个触发器，但普通输出只接最低位。正常模式下计数器不断加一：

```text
内部q：0000 → 0001 → 0010 → 0011 → 0100 ...
可见脚： 0      1      0      1      0 ...
```

如果q[2]永久为0，最低位仍然每拍翻转。只检查这个普通输出，哪怕多跑一些周期，也观察不到这个模型中的高位故障。这就是“可观测性”不足。

内部扫描给这些触发器增加另一条数据入口：

```text
scan_in → q[0] → q[1] → q[2] → q[3] → scan_out
          每来一个时钟，数据往右走一格

scan_enable=0：执行q+1
scan_enable=1：执行移位
```

扫描入口能设置内部状态，叫可控性；扫描出口能读出内部状态，叫可观测性。本实验扫描的是内部状态触发器，和13B的封装引脚边界扫描是不同用途；都可以使用移位思想，但这里没有TAP，也不要求JTAG四线协议。

## 三、扫描逻辑逐行看

```verilog
wire [3:0] proposed = reset ? 4'b0 :
    scan_enable ? {q[2:0],scan_in} : q+4'd1;
```

按优先级阅读：

1. reset为1：下一个状态为0000。
2. 否则scan_enable为1：旧q[2]进入q[3]，旧q[1]进入q[2]，旧q[0]进入q[1]，scan_in进入q[0]。
3. 否则：正常加一。

```verilog
always @(posedge clk)
    q <= fault_enable ? faulty : proposed;
```

只有时钟上升沿到来，触发器才更新。fault_enable是实验注入故障的开关，不是量产芯片一定要有的引脚。

```verilog
assign scan_out = q[3];
```

出口一直连着当前最高位。测试平台先读取出口，再给移位时钟，避免把“移位前的位”和“移位后的位”混淆。

### 手动装入0101，再读出来

装入顺序为最高位在先，四次scan_in分别是0、1、0、1：

```text
从0000开始             q[3:0]
送入0，打一拍            0000
送入1，打一拍            0001
送入0，打一拍            0010
送入1，打一拍            0101  ← 装入完成
```

接下来每次先看scan_out，再移入0：

```text
移出前q    读到q[3]    移位后q
0101          0         1010
1010          1         0100
0100          0         1000
1000          1         0000
```

读到0101就证明了这次位序正确。读取也会改变q，所以需要保留业务状态时，必须另外设计保存/恢复或暂停策略；本实验结束后直接复位重启。

### 不只检查移位，还要捕获一次业务运算

测试平台遍历全部16个初始位型。每个位型做：

```text
扫描装入pattern → 退出扫描 → 执行一拍加一
                 → 回到扫描 → 移出并比较(pattern+1)&15
```

这一步把“设置状态 → 运行组合逻辑 → 捕获结果 → 读出来”连在一起。只是能移位，不代表计数逻辑就正确。

## 四、卡0、卡1如何注入和检测？

“q[2]卡0”在模型里指每次写入状态后，第2位都被强制为0。`fault_bit`选择哪一位，`fault_value`选择卡0还是卡1：

```verilog
wire [3:0] mask = 4'b1 << fault_bit;
wire [3:0] faulty = (proposed & ~mask) |
                   (fault_value ? mask : 4'b0);
```

第一行生成单独一位为1的掩码；第二行先清掉目标位，再按故障值写回0或1。扫描移位和正常计数都通过这条路径，因此故障也可能破坏扫描传输。

默认实际结果见[故障检测矩阵](../../results/20a/REPORT.md)：

| 观察方式 | 检测数/列举故障数 | 原因 |
| --- | --- | --- |
| 正常模式，检查最低位16拍 | 2/8 | 只能看见最低位两种卡死故障 |
| 扫描移入/移出和一次捕获 | 8/8 | 内部四位都能控制、观察 |

每个故障先在正常模式运行，再在扫描模式运行。健康电路必须零不匹配；带故障电路应出现不匹配，驱动脚本把这种“发现错误”记为检测成功。每个扫描案例最后撤除实验注入、退出扫描、复位，再检查8拍正常输出。撤除注入只是验证模式恢复，不意味着真实坏芯片会自愈。

## 五、RAM为什么另外测？

扫描触发器链不自动覆盖RAM内部的所有存储位。RAM需要用地址、读写控制和数据图样访问。

[ram_model.sv](ram_model.sv)中：

```verilog
reg [WIDTH-1:0] memory[0:DEPTH-1];
```

默认代表8个地址，每个地址8位。读写在上升沿发生，读结果在该沿后可用；同一沿又读又写同地址时，代码读到旧值。本实验不依赖同沿写后立刻读，而是将读写拆成独立操作。

```verilog
physical_address = fault_kind==2 ?
    address & ~(1 << fault_bit) : address;
```

这是地址故障注入：指定地址位永远为0。例如bit0坏时，逻辑地址0和1实际都访问0，2和3都访问2。这叫地址别名。

数据故障则对指定数据位施加卡0/卡1；当前模型对所有地址的这一数据位都注入同样故障，代表本实验的数据路径故障集合，不声称逐个枚举了所有物理bitcell故障。

## 六、March C-序列逐步做了什么？

符号`↑`代表地址从小到大，`↓`代表从大到小，r0/r1代表“读取并期望全0/全1”，w0/w1代表“写全0/全1”。

| 阶段 | 顺序 | 每个地址的动作 | 用途 |
| --- | --- | --- | --- |
| 0 | ↑ | w0 | 建立已知初始状态 |
| 1 | ↑ | r0,w1 | 检查零，再翻成一 |
| 2 | ↑ | r1,w0 | 检查一，再翻成零 |
| 3 | ↓ | r0,w1 | 反向访问检查 |
| 4 | ↓ | r1,w0 | 反向翻转并检查 |
| 5 | ↑ | r0 | 最后确认恢复为零 |

默认深度8，因此操作数为`8 × (1+2+2+2+2+1) = 80`，每个案例都检查长度。不是8字节的RAM一定要80拍：这是当前选定序列和一操作一拍的结果。

### 地址0和1别名时，怎样被抓到？

```text
阶段0：把所有位置写0
阶段1：
  逻辑地址0：读0，正确；写1，实际地址0变成1
  逻辑地址1：本应还是0，却也读实际地址0，得到1 → 发现故障
```

### 数据bit0卡0时，怎样被抓到？

```text
阶段1：尝试写0xff，故障模型实际只能存0xfe
阶段2：期望读0xff，实际读0xfe → 发现故障
```

默认枚举16个数据位卡死故障（8位×两种值）和3个地址位卡0别名故障，共19个，检测19/19。每步地址、操作、预期和读值都在对应案例的march.csv里。

## 七、该怎样理解“覆盖率”？

本章的分母都是**显式列出的数字故障模型**：扫描8个，RAM19个。未列举的耦合、桥接、保持、时延、模拟电气故障和整颗SoC的其他逻辑，都不在这个分母里。summary.json保存排除项。

这是DFT原理实验。它没有对19章CPU自动插入扫描，也没有得到工厂可用的ATPG覆盖率或真实存储宏MBIST认可；这些属于21章，需要扫描单元、工具、测试入口和制造方规则。

## 文件与阅读顺序

1. scan_counter.sv：正常计数与扫描移位怎样共用触发器。

4. tb_ram.sv：六个March阶段，每次读如何和期望比较。

## 参数变化也实际跑了一次

除默认8×8 RAM外，还运行了16×4：

| RAM配置 | 数据卡死故障 | 地址别名故障 | 每例March操作数 | 实际检测 |
| --- | ---: | ---: | ---: | --- |
| 深度8、位宽8 | 8×2=16 | 3 | 80 | 19/19 |
| 深度16、位宽4 | 4×2=8 | 4 | 160 | 12/12 |

扫描链仍为同一4位模型，两个参数组均为8/8。结果分别保存在results/20a和results/20a-parameters。变深不一定意味着“列举的数据故障更多”：本模型的数据故障是某个数据位在所有地址上卡死，分母按位宽算；地址故障按地址位数算。

每个扫描案例另有本地scan.vcd波形，CSV保留便于直接阅读和版本追踪的逐周期记录。

## 把示意图对回真实CSV：0101这一组

打开`results/20a/cases/scan-healthy/scan.csv`，找到pattern=5（十进制5就是四位二进制0101）：

| cycle | phase | 输入/输出观察 |
| ---: | --- | --- |
| 87～90 | load | scan_in依次为0、1、0、1，完成装入 |
| 90～93 | unload | scan_out依次为0、1、0、1，与expected一致 |
| 99～102 | capture_unload | 重新装入并执行一拍业务后，移出0、1、1、0，即0110 |

load最后一行和unload第一行同为cycle=90，因为前者是在第90个时钟后记录“装入完成”，后者在下一个移位时钟前读取出口。它们是同一状态的两个观察动作，不是又多执行了一次时钟。

若看`scan-4-test`，故障编号4表示q[2]卡0：编号除2得到位号2，余数得到卡死值0。对照相同pattern的expected和scan_out，就能定位哪次观察首先不匹配。诊断编号只是脚本枚举方式，不是芯片的物理故障地址。
