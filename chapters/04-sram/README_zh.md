# 04 —— 可写 SRAM、栈，以及行为模型背后的硬件

第 03 章只有只读固件存储。本章在字节地址 `0x00010000` 加入 4 KiB Wishbone SRAM。固件检查首末字、更新单独的字节，并调用一个会把返回地址存入 SRAM 的函数。

## 这里的 SRAM 是什么？

系统使用 LiteX 的 `wishbone.SRAM`，它是由 Migen 描述、带 Wishbone 端口的行为存储器。在仿真中它属于生成的 SoC 硬件，不另用一个 SystemVerilog `tb.sv` 重写 SRAM。CPU 发总线事务，LiteX SRAM 模块负责应答。这样测试的总线接口和实际连接的存储器模型处在同一设计里。

这个模型适合验证地址译码、读写、字节使能、初始化假设和固件访问；它不描述某颗芯片的模拟特性、建立保持时间、数据保持、功耗或专有时序角落。

### FPGA 和 ASIC 里怎样接真实存储器？

FPGA 综合时，推断出的存储器或厂商 block RAM primitive 通常会映射到器件内部 RAM 资源。要检查综合结果和时序报告，确认它实际映射到 BRAM，并核对读延迟和写掩码行为。仿真中的 LiteX RAM 本身不能证明 FPGA 已正确映射。

ASIC SRAM 宏通常是由 memory compiler 或晶圆厂库提供的硬宏。它的引脚一般是时钟/使能、地址、数据、写使能或字节掩码、读数据等；通常不直接说 Wishbone。外围 wrapper 把 Wishbone 请求转成这些引脚信号，根据宏的延迟在合适周期返回 ACK 或 ERR。芯片验证中会用功能模型做常规测试，时序、功耗和物理特性另行检查。

### 为什么不把 SRAM 行为写在 testbench 里？

本章要测的是从 CPU 总线到 LiteX SRAM 模块的整条集成路径。如果唯一的存储器实现放在外部 testbench，SoC 本身就没有集成存储器，也可能掩盖设计接口和测试模型之间的不匹配。验证 SRAM wrapper 是否适配厂商宏时，单独的 testbench 模型很有用，但那是另一个测试边界。本章的目标设备就是 LiteX SRAM 模块。

## 为什么固件要设置 `sp`？

栈是普通的可写 RAM，函数调用用它保存需要跨调用保留的状态。本处理器执行 `jal` 时不会自动建立栈帧。软件约定用 `sp`（`x2`）记录当前分配的栈空间；本例的栈向低地址增长。

```text
高地址
0x00011000  选择的栈区顶部
            空隙 / 边界测试字所在区域
0x00010f00  为边界测试字留出空间后的初始 sp
            work 函数分配的 16 字节栈帧，ra 保存在 12(sp)
            更深的调用可继续使用更低地址
低地址
```

入口 `_start` 把 `sp` 设成 `0x10f00`。进入 `work` 后执行 `addi sp,sp,-16`，分配 16 字节栈帧；`sw ra,12(sp)` 保存调用者的返回地址。接着 `jal ra,exercise_sram` 会把新的返回地址写入 `ra`。子函数返回后，`lw ra,12(sp)` 恢复 `work` 自己要用的返回地址，`addi sp,sp,16` 释放栈帧。

### `sp` 和 `ra` 各指向什么？

`ra` 是寄存器 `x1`。`jal ra,target` 把下一条指令地址写入 `ra`，再跳到 `target`。`jalr zero,0(ra)` 跳回 `ra` 保存的地址。嵌套的第二次 `jal ra,...` 会覆盖 `ra`，所以仍需要旧返回地址的函数必须先保存它。

`sp` 是寄存器 `x2`，保存 RAM 中的一个字节地址。它不是函数地址，也不会自动指向函数开头。软件修改 `sp` 来预留栈帧，再用 `12(sp)` 这样的偏移访问帧内的数据。进入 `work` 时调用者的 `sp=0x10f00`；减 16 后当前 `sp=0x10ef0`；返回前加回 16，恢复成 `0x10f00`。

实际编译的 RISC-V 程序可以用寄存器传递参数，只把需要保存的值放进栈帧。函数调用不会自动把所有参数和返回地址压栈。本例手写保存 `ra`，是为了清楚展示它被覆盖和恢复的过程。

### 用递归 `fact(3)` 看每一层栈帧

下面用一个教学用的 RISC-V 约定把变化写具体：参数和返回值放在 `a0`，每层函数手动分配 8 字节，低地址处保存 `n`，高 4 字节处保存旧 `ra`。真实编译器会按 ABI 和寄存器使用情况安排栈帧；这里固定布局是为了看清硬件寄存器与内存各自保存什么。

```c
int fact(int n) {
    if (n <= 1) return 1;
    return n * fact(n - 1);
}
```

假设调用前 `sp=0x1000`。栈向低地址生长。每次进入 `fact`，软件执行 `sp -= 8`，再把本层的 `n` 和 `ra` 写入新栈帧：

```text
高地址
0x1000  调用前 sp（当前还没有 fact 的栈帧）
        ┌──────────────────────────┐
0x0ffc  │ fact(3) 保存的 ret_main  │  ← fact(3) 的 sp = 0x0ff8
0x0ff8  │ fact(3) 保存的 n = 3     │
        ├──────────────────────────┤
0x0ff4  │ fact(2) 保存的 ret_fact3 │  ← fact(2) 的 sp = 0x0ff0
0x0ff0  │ fact(2) 保存的 n = 2     │
        ├──────────────────────────┤
0x0fec  │ fact(1) 保存的 ret_fact2 │  ← fact(1) 的 sp = 0x0fe8
0x0fe8  │ fact(1) 保存的 n = 1     │  ← 最深一层当前 sp
        └──────────────────────────┘
低地址
```

| 时刻 | 正在运行 | 当前 `sp` | `ra` 寄存器此刻的含义 | 栈上保留的内容 |
| --- | --- | ---: | --- | --- |
| 调用前 | 主程序 | `0x1000` | 尚未调用 `fact` | 无 `fact` 栈帧 |
| 主程序调用 `fact(3)` 并建立栈帧 | `fact(3)` | `0x0ff8` | `ret_main` | `n=3`、`ret_main` |
| `fact(3)` 调用 `fact(2)` 并建立新帧 | `fact(2)` | `0x0ff0` | `ret_fact3` | 上层的 `n=3`、`ret_main`；本层的 `n=2`、`ret_fact3` |
| `fact(2)` 调用 `fact(1)` 并建立新帧 | `fact(1)` | `0x0fe8` | `ret_fact2` | 三层各自的 `n` 和返回地址 |
| `fact(1)` 返回 | `fact(2)` | `0x0ff0` | `ret_fact2`，用于回到 `fact(2)` 的乘法处 | `a0=1`，`fact(3)` 与 `fact(2)` 的帧仍在 |
| `fact(2)` 算出 `2×1`，恢复旧 `ra` 并返回 | `fact(3)` | `0x0ff8` | 从 `fact(2)` 的保存槽恢复为 `ret_fact3` | `a0=2`，只剩 `fact(3)` 的帧 |
| `fact(3)` 算出 `3×2`，恢复旧 `ra` 并返回 | 主程序 | `0x1000` | 从 `fact(3)` 的保存槽恢复为 `ret_main`，随后跳回 | `a0=6`，所有 `fact` 栈帧释放 |

这里最关键的是 `sp` 不是函数地址。调用 `fact(2)` 时，`fact(3)` 的帧仍留在 RAM；新的 `sp` 指到更低地址，为 `fact(2)` 留出另一块空间。返回时，当前层读回自己保存的 `ra`，再把 `sp` 加回 8，上一层的帧就重新成为当前帧。

从硬件角度看，`jal ra, fact` 只做两件事：把下一条指令地址写进通用寄存器 `ra`，并把 `pc` 改到 `fact`。`addi sp,sp,-8` 是一次普通寄存器运算；保存 `n`、`ra` 的 `sw` 则是 CPU 发出的普通数据总线写事务。处理器没有“自动压栈”这条隐藏动作。保存规则来自软件；硬件只执行这些指令。

## 常见问题

### 这个测试只有一个小函数，为什么还要栈？

嵌套调用能直接展示返回地址的生命周期：`_start` 调 `work`，`work` 再调 `exercise_sram`。第二次调用会改写 `ra`；先把旧 `ra` 存入 SRAM，`work` 才能正确返回 `_start`。递归、中断，以及任何还要继续调用其他函数的函数都会遇到类似需求。

### 固件对 SRAM 做了什么？

先向首字写 `0x11223344`，把最低字节改成 `0xaa`，再把高两个字节改成 `0xbbcc`，最后预期读到 `0xbbcc33aa`。它还会写入并读回末字 `0x00010ffc`。函数调用使用 SRAM 中另一个栈区域。

### SRAM 太小时怎样抓到错误？

运行器再用只有 256 字节的 SRAM 跑同一个程序；程序使用的测试地址和栈空间已超出容量。VexiiRiscv trap handler 读取 `mcause`，把它写到完成端点，并报告 store access fault（`mcause=7`）。运行器要求出现故障标志，同时拒绝正常完成标志。这样错误由 CPU 的架构异常明确报告，而不是只看到仿真超时。

## 运行与观察

```sh
PYTHONHASHSEED=0 python3 chapters/04-sram/run.py
```

正常的 4 KiB 运行应通过读回检查；256 字节负例应报告预期 store fault。查看 `results/04/` 和 `results/04-small-ram/` 下的固件镜像、地址表、日志和 VCD。这个 32 位、按字寻址的 Wishbone 接口上，字节地址 `0x10000` 对应字地址 `0x4000`。

## PASS 能证明什么？

正常 PASS 检查了仿真 SRAM 的首末位置、字节通道和栈访问。负例 PASS 检查了容量不足时固件报告 store access fault。它不证明某颗 FPGA BRAM 或 ASIC SRAM 宏的物理时序；那要使用具体存储器实现和对应验证流程。
