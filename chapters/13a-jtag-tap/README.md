## JTAG 最初干什么？

芯片焊到板上以后，有些焊点藏在封装下面，很难用探针接触。JTAG 的边界扫描让外部测试器控制芯片输出、采样芯片输入，从而检查芯片间连线。IEEE 1149.1 的目标包括装配后的板级互连测试。[IEEE 工作组说明](https://grouper.ieee.org/groups/1149/1/index.html)

```text
外部测试器 --> 芯片 A：输出 1 --> 板上连线 --> 芯片 B：采样是否为 1
           --> 芯片 A：输出 0 --> 板上连线 --> 芯片 B：采样是否为 0
```

后来这条串行入口也被用于配置 FPGA、访问内部状态和传输 CPU 调试请求。入口后面要有相应硬件，才能提供对应功能。

本章先学习这个入口，下一章再接上与 IO 相连的测试单元。

```text
Python 决定访问步骤
     |
SV 测试台把步骤变成四根线的电平
     |
     v
TAP 控制器：选择路径、安排传输
     |
     +--> IDCODE：固定的教学标识
     +--> USER：可以读写的内部寄存器
     +--> BYPASS：一位的旁路
```

## 四根线各自干什么？

先把方向画出来，“输入”始终相对于被访问的芯片：

```text
电脑上的测试器                            芯片里的 TAP

          TCK：什么时候推进一拍 ---------> 时钟入口
          TMS：这一拍往哪个状态走 --------> 状态机
          TDI：这一拍送进去的一个比特 ----> 移位寄存器
          TDO：这一拍读出来的一个比特 <---- 移位寄存器
```

TMS 不是要写的数据；它决定状态机的路线。TDI 才携带要写入的位。TCK 由外部测试器提供，与前面 SoC 的系统时钟可以不同。

实验另有可选的低有效 `trst_n`，用于直接复位 TAP。四线操作仍能通过 TMS/TCK 复位。接口方向和状态路径可参考 [AMD JTAG 引脚说明](https://docs.amd.com/r/en-US/am011-versal-acap-trm/JTAG-Controller-Interface-Pins)。

## IR 和 DR 为什么要分开？

IR 是 **Instruction Register，指令寄存器**。这里的“指令”表示选择哪条测试路径，例如“读取 IDCODE”；它不是 CPU 执行的 RISC-V 指令。

DR 是 **Data Register，数据寄存器**。IR 选定某个功能后，DR 扫描就读写该功能的数据。

```text
                 先扫描 IR：选择功能
                           |
                           v
                      IR 的译码
                  /         |        \
            IDCODE       USER        BYPASS
             32 位        32 位        1 位
                  \         |        /
                   当前 DR 串行通路
                   TDI ---> ... ---> TDO
```

例如，先把本例的 `0x3` 写入 IR，接下来的 DR 扫描才会访问 USER 寄存器。这个 `0x3` 是我们选的编码；不能拿它直接控制另一个厂家的芯片。

## 先手算一次移位

先用一个 **4 位纸上例子**看动作。真实 IDCODE 仍是 32 位。

```text
                    旧值：b3 b2 b1 b0
                          1  1  0  1

TDI=0 --> [新位进入高位，原来的各位向右移动] --> TDO=旧 b0
```

| 拍数 | 上升沿前的值 | TDI | 读出的 TDO | 移位后的值 |
| --- | --- | --- | --- | --- |
| 1 | 1101 | 0 | 1 | 0110 |
| 2 | 0110 | 0 | 0 | 0011 |
| 3 | 0011 | 0 | 1 | 0001 |
| 4 | 0001 | 0 | 1 | 0000 |

收到的顺序是 `1,0,1,1`，第一位应放回 bit0，重建得到 `1101`。把第一位误当 bit3，会重建成 `1011`。

**读出和移入同时发生。** 即使只想读取 IDCODE，也要给 TDI 一个确定的值；本例读取时输入零。

本模型在 TCK 下降沿准备下一位 TDO，测试器在下一次上升沿前采样。上升沿完成状态推进与移位。测试台保留了信号稳定和检查的时间；仿真中的纳秒延迟是激励设置，不是板卡下载速度。

## 不用背 16 个状态，先认三种动作

| 动作 | 硬件在做什么 | 好理解的说法 |
| --- | --- | --- |
| Capture | 把要读的并行值装入移位寄存器 | 拍一张快照 |
| Shift | 每拍移入一位、移出一位 | 沿四根线串行传输 |
| Update | 把移入完成的值提交给目标寄存器 | 正式生效 |

USER 的输出值在 Shift 时不会随着每一位输入立即变化。只有走到 Update-DR 并执行更新，它才接收完整移位结果。这让外部传输与内部可见值分开。

从空闲进入 DR 的路线：

```text
IDLE --TMS=1--> SELECT_DR --0--> CAPTURE_DR --0--> SHIFT_DR
                                                        |
                                  继续移位：TMS=0 <------+
                                                        |
                                  最后一位：TMS=1        v
                                                    EXIT1_DR
                                                        |
                                                        1
                                                        v
                                                    UPDATE_DR
                                                        |
                                                        0
                                                        v
                                                       IDLE
```

进入 IR 时在 SELECT_DR 再给一次 `TMS=1`，就走向 SELECT_IR、CAPTURE_IR、SHIFT_IR。IR 路线也有 Capture、Shift、Update。

**最后一个比特那拍仍然移位。** 它的 TMS=1 表示“完成本拍后离开 Shift”，不能漏掉最后一位。

模型按上升沿前的状态执行动作。例如 CAPTURE_DR → SHIFT_DR 那拍执行 Capture；UPDATE_DR → IDLE 那拍提交值。CSV 同时记录 `pre` 和 `post`，因此要结合两列看硬件动作。

## 按顺序做三个实验

### 实验一：没有 CPU，读一个内部值

`idcode` 场景复位 TAP，进入 DR 扫描，读出 32 位，重组为默认 `0x12345679`。这说明入口和标识路径工作正常；标识是教学值，不是真实厂商器件 ID。

先在可视化里停在 CAPTURE_DR，随后找到 SHIFT_DR，看看 TDO 每拍变化。前八位为 `1,0,0,1,1,1,1,0`，第一位放回 bit0，组成低字节 `0x79`。

### 实验二：读旧值，同时写新值

`user-register` 场景先通过 IR 选 USER，再通过 DR 送入新值：

```text
                 正式 USER 值     传输用副本          外部读回
Capture          cafef00d         复制 cafef00d       —
Shift 32 拍      cafef00d         旧位出、新位进      cafef00d
Update           2468ace1         完整新值            —
下一次扫描       2468ace1         复制后逐位读出      2468ace1
```

源寄存器和移位寄存器是两组硬件。Capture 一次复制完整值，后面慢慢读副本；Shift 不会让正式值变成“只写了几位”的半成品。第二次扫描输入零，Update 会把 USER 写成零，因此这里读取有写入副作用。

### 实验三：少读一位，为什么数值还能对？

`short-scan` 只取 31 位，默认 IDCODE 的最高位刚好为零，重组出的整数仍是 `0x12345679`。检查器对照要求的 32 位，抓到 `SHORT_SCAN`。

```text
数值正确 + 长度错误 = 本次传输没有完成
```

负例报告 PASS 表示预设错误被抓到。另有选错 IR、反向理解位序、扫描中复位、暂停恢复的实验，详见 `summary.json` 和本章 [时序与检查参考](REFERENCE.md)。

## 到这里应该理解什么？

- TAP 是外部访问控制器，IR 选择功能，DR 传输所选功能的数据。
- Capture 取副本，Shift 逐位交换，Update 提交。
- 四根线只是一条入口；下一章接上边界单元后，才会影响被测 IO。
- 先理解一次完整访问，再查 16 状态的路线；默认 10 场景检查 32/32 状态转移。
