# 13A 参考：快照、复位、参数与故障证据

完成 README 的基础实验后，再查阅这里的细节。系统计数器、错误锁存与跨系统时钟交接为扩展设计示例，当前 TAP 没有接入这些系统信号。

## 寄存器一直在变，怎么把完整的值读出来？

**先在一个时钟沿复制整个值，再慢慢送出这份副本。** 读出的值代表 Capture 那一刻，不代表最后一位送出时的值。原寄存器可以继续工作。

```text
工作中的寄存器                 专门用于传输的寄存器
可能不断变化                   Capture 时装入一份副本
     |                                  |
     +------ Capture：并行复制 ----------> dr_shift
                                         |
                              Shift：每拍送出最低位
                                         |
                                         v
                                        TDO --> 测试器重组完整数值
```

这里有两组真正的硬件寄存器，不是软件在循环读取每一位。本章 USER 路径对应两句 RTL：

```verilog
// Capture-DR：在一个 TCK 上升沿，把整个 32 位值装入传输寄存器。
dr_shift <= user_data;

// Shift-DR：之后每拍只移动这份副本，同时接收 TDI。
dr_shift <= {tdi, dr_shift[31:1]};
```

Shift 时没有再次读取 `user_data`。`dr_shift` 的数值会随着移位改变，但送出的各位都来自同一次 Capture。下面用三个场景看这件事。

### 场景一：计数器已经从 13 数到 20，我为什么仍然读到 13？

假设我们增加一个计数器读出功能，用 **4 位教学值**说明，Capture 时计数器为 `1101`，也就是 13。暂且假设采样能保证完整、稳定；跨时钟的处理在后面解释。

| 动作 | 正在运行的计数器 | 传输副本：动作前 → 动作后 | 测试器收到 |
| --- | --- | --- | --- |
| Capture | 13 | 任意值 → `1101` | 尚未读出 |
| 第 1 拍 Shift，TDI=0 | 14 | `1101` → `0110` | bit0 = 1 |
| 第 2 拍 Shift，TDI=0 | 16 | `0110` → `0011` | bit1 = 0 |
| 第 3 拍 Shift，TDI=0 | 18 | `0011` → `0001` | bit2 = 1 |
| 第 4 拍 Shift，TDI=0 | 20 | `0001` → `0000` | bit3 = 1 |

外部按 bit0 到 bit3 收到 `1,0,1,1`，重组成 `1101`，也就是 **13**。过程中计数器继续增加，不影响这次读数。再做一次 Capture，才会得到下一份快照。

这些计数值只是演示时间关系，并不规定系统时钟与 TCK 的频率比例。本章实际没有这个计数器；实际的 IDCODE 是常量，USER 只在 Update 或外部复位时改变。

### 场景二：读旧 USER，同时写入新 USER

这是本章已经运行的实验。选择 USER 后，第一次扫描送入 `0x2468ace1`，期望读出初值 `0xcafef00d`：

```text
                  user_data              dr_shift                 外部读到
Capture           cafef00d               cafef00d                 —
32 拍 Shift       仍然是 cafef00d        旧位移出，新位移入       cafef00d
Update            变成 2468ace1          2468ace1                 读数已完成
下一次 Capture    2468ace1               2468ace1                 —
下一次 Shift      2468ace1               开始移位                 2468ace1
```

**一次扫描可以读出旧值，同时准备新值。** 但新值直到 Update 才生效，因此不会出现“写到第 8 位，内部就先使用一个只写了一部分的值”。

本章第二次扫描输入的是全零，所以读出 `0x2468ace1` 后，Update 会把 USER 写成零。这里的 USER 是可读写路径，不能把“读取时 TDI 给零”当成没有副作用。若要保留已知旧值，可以在扫描时把同一个值移入；真正只读的状态路径则应设计成 Update 不修改源寄存器。本章 IDCODE 就不会被扫描输入改写。

### 场景三：想抓到一次错误，为什么普通 Capture 可能错过？

假设总线错误信号只保持一个系统时钟周期，而我们稍后才通过 JTAG 读取：

```text
系统时间 -->       出错                     JTAG 开始 Capture
error              0 -> 1 -> 0             此时已经是 0
直接读 error                                只能读到 0

错误记录寄存器     0 -> 1 ----------------> 仍然是 1
                   同时保存出错地址          Capture 这份记录，再 Shift 送出
```

Capture 只能采样当时的值，不能找回已经消失的脉冲。要回答“之前有没有错、错在哪个地址”，需要在系统时钟域中先保存事件，例如：出错时置位 `error_seen`，同时锁存 `error_address`；读完后再用明确的清除命令释放记录。也要规定后续错误是覆盖旧记录还是保留第一次错误。

这属于未来接入 SoC 时需要增加的功能，本章 TAP 尚未连接总线错误信号。**TAP 负责把记录送出来；负责发现和保存错误的是系统里的监测逻辑。**

### TCK 和系统时钟不同，复制会不会撞上变化？

会。比如系统计数器从 `0111` 变成 `1000`，多个位都要翻转；直接用另一个时钟采样，可能读到不属于这两个值的组合。快照寄存器解决“传输期间还在变化”的问题，但跨时钟时还需要保证“拍下来的值本身完整”。

一种常见做法是让系统时钟域先保存快照，再通知 TAP 来取：

```text
TCK 域：发出快照请求  --------------------> 系统时钟域：收到请求
                                             |
                                             v
                                      保存完整值，并保持不变
                                             |
TCK 域：收到完成通知  <--------------------+
        |
        v
把稳定快照装入 dr_shift，再逐位送出
传完后允许系统释放快照
```

请求和完成通知需要跨时钟同步，快照数据要在交接期间保持稳定。给每一位各加两级同步器，不能保证多位数据来自同一个时刻。另一条路线是让调试桥在系统时钟域完成一次总线读取，再把返回值交给 TAP。

本章 `user_data` 和 `dr_shift` 都由 TCK 驱动，因此还没有这条跨系统时钟的通路，也不需要先停住 CPU 才能完成当前实验。

## 复位与暂停怎么理解？

任意 TAP 状态下，持续 `TMS=1` 并推进至少五个 TCK，可以进入 Test-Logic-Reset。这是 TAP 状态机定义的复位路径；不是我们随便选的次数。[AMD 配置指南](https://docs.amd.com/api/khub/documents/FOs3lXmlcWxBhTIFxVKyGA/content)

本例此时把 IR 选择恢复成 IDCODE。**TAP 复位不表示 CPU、RAM 或整颗 SoC 已复位。** 当前 TMS 复位也不把 USER 的值强行清零；`trst_n` 在本教学模型里会初始化 USER。两种复位的作用由代码明确规定。

Pause-DR 保存当前移位进度。返回 Shift-DR 后，可以继续取剩下的位。本章先取 8 位，暂停，再取 24 位，组合检查完整的 32 位结果。

注意：用 TMS 离开一个未完成的扫描，途中可能经过 Update。不能把“最后回到 Reset”理解成“之前部分写入保证没有副作用”。本章恢复检查关注状态、IR 选择以及随后完整 IDCODE 扫描。

## 哪些数字是参数，哪些由协议规定？

| 数字 | 当前值或约束 | 来源 |
| --- | --- | --- |
| 状态数量 | 16；每个状态有两条 TMS 路线 | 标准 TAP 状态图 |
| TMS 复位 | 至少 5 拍连续高 | 标准状态图保证 |
| IR 长度 | 默认 4 位，工具接受 4–16 位 | 本教学实现选值；真实器件查文档 |
| IDCODE 扫描长度 | 32 位 | IDCODE 寄存器格式 |
| IDCODE 数值 | 默认 `0x12345679`，可更改 | 教学值，不代表真实厂商或芯片型号；bit0 保持 1 |
| IDCODE / USER 编码 | `0x2` / `0x3` | 本例选值，非通用编码 |
| USER 数据宽度 / 初值 | 32 位 / `0xcafef00d` | 本例实现选值 |
| BYPASS | 1 位；IR 的全 1 编码选中 | BYPASS 通路定义；其他未知编码在本例也走 BYPASS |
| 32/32 状态转移覆盖 | 16 个状态各测 TMS=0、1 | 本工具的状态图检查；不代表全部时间关系已验证 |

IDCODE 与 BYPASS 的不同扫描宽度见 [TI JTAG 应用说明](https://www.ti.com/lit/an/spma075/spma075.pdf)。

## 错误是怎样被 capture 到的？

Python 先生成 TMS/TDI 激励；SV 测试台真的驱动 TAP，读取 TDO 和状态。Python 再从日志取出指定扫描的位，重建数值并检查长度。状态期望由独立的状态表给出，读回期望来自已知寄存器值。

| 场景 | 真正做了什么 | 捕获证据 |
| --- | --- | --- |
| 正常 IDCODE | 复位后读取完整 DR | 32 个采样位重建为指定 IDCODE |
| Capture-IR | 扫描 IR 并选择 IDCODE | 读回低位捕获模式 `01`，后续 IDCODE 正确 |
| USER 写读 | 移入 `0x2468ace1`，Update 后再读 | 先读旧值，下一次读新值 |
| BYPASS | IR 写全 1，输入已知位串 | TDO 相对 TDI 延迟一拍，首位为 0 |
| 错误 IR | 本想读 IDCODE，却选 `0x4` | 实际进入单比特 BYPASS，读回不符，记 `WRONG_IR_READBACK` |
| 少移一位 | 只读 31 位，却要求完整 32 位 | 采样数量不符，记 `SHORT_SCAN`；不能只比较数值 |
| 位序理解错误 | 读取 USER，却把首位当最高位 | 错误重建值不符，记 `WRONG_BIT_ORDER` |
| 扫描中复位 | USER 只移 8 位就复位，再重新读 IDCODE | 部分扫描记 `RESET_INTERRUPTED_SCAN`，随后完整扫描正确 |
| Pause / Resume | 8 位后暂停，再读 24 位 | 合并后的 32 位与原值一致 |
| 全状态图 | 到达每个状态，分别走两条出边 | 每拍 pre/post 与状态表一致，共 32 条边 |

三种“故意读错”和部分扫描会被检查器判为不完整或不符。整个负例场景报告 PASS，表示 **工具确实抓到了预设错误**。其他场景中出现同类错误，会直接停止并判失败。

`idcode.csv` 开头记录复位与进入 DR 的过程，后面 32 行是扫描位。例如默认 IDCODE 的前八个 TDO 位为 `1,0,0,1,1,1,1,0`，对应低字节 `0x79`。读者可以逐行手算，再和 `summary.json` 对照。
