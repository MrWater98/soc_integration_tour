# 6. 读真实结果：正确、被检测的错误、以及加速成本

## 6.1 先看计算结果，不先看性能

results/13f/run.log中：

```text
CFU_DOT result=13
CFU_DENSE_0 result=28
CFU_DENSE_1 result=0
CFU_RANDOM_CHECKS count=64
CFU_COMPLETE code=0x0000005a commands=619 responses=619
```

它们来自真实VexRiscv RTL执行固件，再写Wishbone日志端点，不是Python先算好后直接打印。这次Verilator模型使用1MHz时钟；主机运行速度和实际芯片性能是另一回事。

## 6.2 为什么是619条命令？

每次点积有1条清零，加上ceil(n/4)条MAC。把main.c实际调用相加：

| 来源 | 数量 |
| --- | ---: |
| 最初4项点积 | 1清零+1 MAC=2 |
| 两个8项输出 | 2×(1+2)=6 |
| 64组长度1～17的随机对拍 | 64次清零+163条MAC=227 |
| 64次普通CFU计时 | 64×3=192 |
| 64次预打包CFU计时 | 64×3=192 |
| 总计 | 619 |

run.py要求观察计数必须符合这个数。源码中只有5个静态CUSTOM0位置，但循环会反复执行，所以不能把5条反汇编位置当作只执行过5次。

软件模拟模式没有CUSTOM0，也没有接受的CFU命令，仍然输出相同结果。这条对照能帮助确认宏切换确实生效。

## 6.3 独立RTL实验的预期值谁来算？

Python把输入word拆成四个字节，恢复有符号值，加128，与对应权重相乘，再更新参考累加器。每行vectors.txt包含：

```text
function_id input0 input1 expected hold_cycles
008         00000000 00000000 00000000 2
000         84838281 0103ff02 0000000d 4
```

第一行清零；第二行算13，并故意让接收方暂停4拍。硬件结果必须稳定保持，直到rsp_ready=1消费。

前4组是固定边界/示例，其后2000组由seed=13生成。不是所有输入组合的穷举，也不宣称覆盖所有CPU或神经网络算子。

## 6.4 CSV里哪个值是时钟前、哪个是时钟后？

打开direct/cfu_cycles.csv：

- accepted_cmd、accepted_rsp：本次沿之前valid&ready是否同时为1。
- cmd_ready_before、rsp_valid_before等：采样沿之前的状态。
- result_before：本次沿之前的累加器。
- result_after：本次沿之后更新的累加器。

接受命令后rsp_valid变1、cmd_ready变0是正常现象。不能只看沿之后ready=0，就断言本次命令未被接受。

响应等待期间，result_after应该连续保持相同；reset会清状态并丢弃未交付响应。本地cfu.vcd也保留波形，CSV是较容易直接阅读的版本。

## 6.5 故意把offset改错，怎样抓到？

测试脚本只在结果目录生成一个坏副本，将InputOffset从128改成0；原始upstream/cfu_mac.v及其哈希不变。

known向量本应算13。移除加128后，四个q值直接乘权重：

```text
原来：Σ(q+128)×w = 13
现在：Σq×w       = 13 - 128×Σw
本组权重和：2-1+3+1 = 5
错误结果：13-128×5 = -627
```

实际negative/run.log报：

```text
MAC_MISMATCH vector=1 actual=fffffd8d expected=0000000d
```

0xfffffd8d就是32位二补码-627。vector从0开始，第一组为清零，因此vector=1是第二组。脚本必须看到这个指定不匹配才认为负例通过；坏核心若仍PASS，整章测试会失败。

## 6.6 为什么硬件版反而更慢？

本次64次、每次8元素点积：

| 路径 | 周期 | 计入哪些工作 |
| --- | ---: | --- |
| 普通C参考 | 10971 | 读取8个输入/权重、标量乘加、循环、结果写入 |
| 普通CFU调用 | 24859 | 读取数组、每次打包、清零、两条MAC、循环、结果写入 |
| 预打包CFU循环 | 727 | 操作数在计时前准备好；清零、两条MAC、循环、结果写入 |

第一种和第二种都从数组开始。对这么短的向量，打包的移位、循环、函数调用和CFU调度成本超过了省下的计算时间。因此不能看到用了并行乘法器就假定程序一定变快。

第三种把准备数据移到了计时范围外，展示计算内核在操作数就绪后的开销。它不是从原始数组到网络输出的端到端耗时。不能直接宣传“整个网络加速约15倍”；数组准备、权重切换、内存带宽、bias/ReLU以及网络其余算子都没有计入这个727。

量化网络常会在模型导出或数据布局阶段预先打包权重，但输入如何准备、能复用几次、RAM带宽够不够，必须另外测量。当前CFU没有DMA，全部操作数仍由CPU提供。

## 6.7 软件模拟模式有什么价值？

同样64次循环，软件模拟CFU路径实际记录为40817周期，预打包软件CFU循环为16513周期，普通C参考为10991周期。它展示软件模拟有自己的函数与拆包成本，不是硬件周期的替代估计。

两份程序的代码布局、缓存状态等也可能变化，所以普通C参考的10971和10991不完全相同。当前只做一次受控运行，没有多次统计分布或板上功耗测量；不要把几个周期的差别当作稳定结论。

## 6.8 下一步可以扩展什么？

先优化数据布局、避免反复打包，再讨论更多lane、片内缓冲、DMA或完整卷积。若引入TFLM，还需把具体算子实现替换进推理路径，处理scale/zero_point/重定标，并验证完整模型输出。若上Tang Primer，还需另测full+cfu系统的资源、DSP映射和时序，当前没有替板卡作出保证。

本章的完成证据是现成核心、真实CPU调用和算子对拍；它不是整个NPU、整网性能或ASIC流片完成的证据。
